# Kotoro Analytics on Kind

Kustomize manifests for running the Analytics API, the Analytics Consumer and the
analytics read database on a local [Kind](https://kind.sigs.k8s.io/) cluster.

| Resource | Kind | Notes |
| -------- | ---- | ----- |
| `postgres-analytics` | StatefulSet + Service | read database, 1 Gi PVC |
| `analytics-migrations` | Job | `alembic upgrade head`, retried until the database is up |
| `analytics-api` | Deployment (2) + Service | liveness `/healthz`, readiness `/readyz` |
| `analytics-consumer` | Deployment (1) | RabbitMQ → projections, safe to scale out |
| `rabbitmq` | Deployment + Service | **development only**, see below |
| `analytics-config` / `analytics-secrets` | ConfigMap / Secret | generated by Kustomize |

Every analytics pod runs as non-root (uid 1000) with a read-only root filesystem, no
Linux capabilities and the `RuntimeDefault` seccomp profile.

## Ordering without `depends_on`

Kubernetes applies everything at once. The API and the consumer have an
`initContainer` that runs `python -m kotoro_analytics.infrastructure.database.wait_for_schema`
and only lets the pod start when the database is at the latest Alembic revision. This
matters most for the consumer: on an empty schema it would reject, and lose, the first
events.

## Run

Requirements: Docker, [kind](https://kind.sigs.k8s.io/docs/user/quick-start/#installation),
`kubectl`.

```bash
kind create cluster --name kotoro

# Image built locally and loaded into the cluster (no registry needed)
docker build -t kotoro-analytics:0.1.0 analytics
kind load docker-image kotoro-analytics:0.1.0 --name kotoro

# Secrets: copy the example and change every value
cp deploy/kind/analytics/secrets.env.example deploy/kind/analytics/secrets.env

kubectl apply -k deploy/kind/analytics
kubectl -n kotoro-analytics wait --for=condition=complete job/analytics-migrations --timeout=180s
kubectl -n kotoro-analytics rollout status deploy/analytics-api deploy/analytics-consumer
kubectl -n kotoro-analytics get pods

# Reach the API from the host
kubectl -n kotoro-analytics port-forward svc/analytics-api 8001:80
curl http://localhost:8001/readyz
```

Logs (JSON, one object per line):

```bash
kubectl -n kotoro-analytics logs deploy/analytics-api
kubectl -n kotoro-analytics logs deploy/analytics-consumer
```

Clean up: `kind delete cluster --name kotoro`.

## Production mode

`ANALYTICS_ENVIRONMENT=production` is set on purpose: the API refuses to start without
`ANALYTICS_JWT_SECRET` (min. 32 characters) and the seed script refuses to run. The JWT
secret must equal the Go API's `JWT_SECRET`, otherwise every request is `401`.

## What is still missing

- **Shared RabbitMQ and Go services.** `rabbitmq-dev.yaml` is a throwaway broker so the
  consumer can run on its own. When the Go API, the Outbox Relay and RabbitMQ get their
  manifests, remove it from `kustomization.yaml` and point `ANALYTICS_RABBITMQ_URL` to the
  shared broker.
- **Ingress.** Access is through `kubectl port-forward` for now.
- **Secrets management.** `secrets.env` is a local file (git-ignored); a real cluster
  should use an external secret store.

## Validation

The manifests were rendered with `kubectl kustomize` and validated with
[kubeconform](https://github.com/yannh/kubeconform) against Kubernetes 1.31 in strict
mode (11 resources, 0 invalid). The image was exercised with the same restrictions
(`--read-only --user 1000 --cap-drop ALL --security-opt no-new-privileges`):
`wait_for_schema`, the API and the consumer start and stop cleanly. The manifests have
not yet been applied to a real Kind cluster from this machine (kind is not installed).
